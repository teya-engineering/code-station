# ADR-0003: The station host and its clients

## Status

Accepted. The daemon, the TUI as a client, the GUI as host, host events and handover are built.

## Context

One process owns the station's files at a time, through the station lock (ADR-0002). Until now the owner was also the only front end. The GUI and the TUI shut each other out, a terminal could not follow a session the GUI was running, and quitting either one ended its sessions.

The station already sits behind one interface, `StationInterface`, with the engine (`StationCommands`) serving each client its own `StationConnection`. Every command answers with plain Codable values in the phone remote's vocabulary. What was missing was a way to reach that interface from another process, and a process to own the station when no GUI is open.

## Decision

### Roles

- **Station host:** the process that holds the station lock. It owns the store and the session runner and serves the station on a local socket. `code-station daemon` is a host. So is the GUI while it holds the station: it serves the same socket from the store and runner its windows use (`GUIStationHost`), and keeps its direct use of the engine.
- **Client:** a front end that drives the station through the socket. The TUI is always a client, even when it started the daemon itself. The phone stays on its own LAN server for now.

### The socket

- **Transport.** A Unix domain socket beside the station lock (`station.sock`). If that path would be longer than `sun_path` allows (103 bytes plus the terminating zero), the socket goes in the user's temporary folder under a name hashed from the preferred path, so each station still gets its own. The host replaces whatever was at the path when it starts, since it holds the lock.
- **Who may connect.** The socket file is mode 0600, set before the socket listens. The host also checks each peer's uid with `getpeereid` as it connects, and refuses another user before reading anything.
- **Framing.** Newline-delimited JSON, one object per line. There is no WebSocket framing.
- **Handshake.** The client sends its protocol version and build version, and the host answers with its own or with a refusal naming both. Both must match exactly. The GUI and the terminal binary ship in one bundle, so a mismatch means two installs or a development build against an installed app, and a refusal is clearer than odd behaviour. A refused handshake is final: the client does not retry.
- **Handshake timeout.** A host can take a connection and never answer it: one that has stopped accepting while it hands over (the GUI quitting with a turn still running) leaves the connect queued in its listen backlog. So a client that has no answer to its hello within 3 seconds lets that attempt go, says the station is not answering through `linkUpdates()` on the station interface, and keeps trying as it does after losing a host, re-reading the lock each time. It attaches to whichever host answers next, such as the daemon taking over. After 20 seconds without an answer it names the holder from the lock, with its kind and pid, and how to stop it (`kill <pid>`). Both limits run on the suspending clock, so a Mac that sleeps through them does not trip them. Discovery hands back a client in this state rather than waiting on it, and the TUI shows the notice at the head of its sidebar until the host answers, instead of a blank frame. Commands asked meanwhile are refused with the same notice.
- **Requests.** Each request carries an id. The host answers each with the same id and either a value or a `StationRefusal`. It starts one client's requests in the order they came, each as soon as it arrives, so a slow command (reading changes, syncing, finding in files, creating a worktree) holds up nothing the client asks for next, such as a stop or a permission answer. Commands that answer at once still finish in order, as they would in process. Only what opens, closes or ends a stream (subscribing, unsubscribing, opening and closing a session, disconnecting) keeps strict order: those run one after another, so a stream is never closed before it opens.
- **Subscriptions.** A request that opens a stream (the live list, an open session) is answered first, and the stream starts only once that answer has gone, so an open session's snapshot always arrives before any patch to it. The host then pushes what the stream sends, and each push names the request's id as its subscription. An open session's stream ends with an `ended` push. Snapshots and patches are the existing remote types, applied on the client with `RemoteTranscript`.
- **One place per command.** The wire vocabulary is one Codable enum, `StationRequest`, with one case per command and a `perform` that runs it on the client's `StationConnection`. A new command adds a case, a line in `perform`, and the method in `StationSocketClient` that sends it.
- **Reuse.** `StationSocketServer` takes a `StationCommands` and a path, and knows nothing about daemons, so the GUI runs the same server in-process. The contract suite runs every scenario against the in-process client, against the socket client of a server started in the test, and against the socket client of a server set up as the GUI sets it up, so they cannot drift apart.
- **Host events.** What a host's runner tells the person (a turn that ended, a question waiting, a wait gone stale, taking those back, the session sound) also goes to every client that subscribes to host events. `StationCommands` puts a relay in front of its runner's services: each call still reaches the host's own services (the GUI's notifications, nothing for the daemon), and is sent as a `StationHostEvent` to every listener. A client hands each event to its own services, so the TUI rings the bell and posts OSC 9 whichever host runs the session. Events while a client is away are not replayed.
- **The GUI's screen.** The GUI's engine is built with `showsSelection`, so a turn that ends in the session it has selected, while it is the active app, is read, as before. The daemon has no screen of its own.

### Discovery and lifecycle

- **The lock records the socket.** The lock's holder record gains `endpoint`. A host claims the lock first, starts listening, and then writes the endpoint. A record with no endpoint means a host that is still starting, or one that serves no clients.
- **Reading the holder.** A front end reads the record without trying to take the lock. Probing with `flock` would make a daemon's own claim fail while a front end polls. A record naming a dead pid counts as nobody.
- **The TUI.** It reads the lock. If a live host has recorded an endpoint, the TUI connects there, or, if that host does not answer the handshake, starts anyway and says so while its client keeps trying. If nobody holds the station, it starts `code-station daemon` from its own binary and polls until the endpoint appears. The daemon runs detached, in its own session (`POSIX_SPAWN_SETSID`) with its standard streams on `/dev/null`, so closing the terminal does not stop it. A holder that never records an endpoint, such as a GUI from before it served the socket, is named in a refusal once the wait runs out. Quitting the TUI closes its socket and leaves its sessions running.
- **The daemon.** It follows the station preferences, claims the lock, and starts the core with `SilentHost`, since nobody sits in front of it. It serves the socket and records the endpoint. On SIGTERM or SIGINT it stops serving, runs the quit sweep and saves, clears the endpoint and releases the lock. It does the same once it has had no clients and no busy session for its grace period: 10 minutes by default, or `CODE_STATION_IDLE_EXIT` seconds.
- **Reconnecting.** When the host goes away, a client refuses every request still waiting, then keeps trying the endpoint, re-reading the lock each time. Once a host answers, it subscribes to the list again, opens every session it had open again (each stream carries on from a fresh snapshot) and says again what it shows. A client does not start a daemon of its own when a host disappears. Until a host returns, its commands are refused with a message saying it is reconnecting. A host that comes back but refuses the handshake (a host of another build took the station) is final, as at first connect: every stream the client handed out ends, and every command is refused with the reason. The TUI then shows that reason in its sidebar instead of the list it can no longer follow.

### Handover

- **On the host handing over.** The engine (`StationCommands`) hands over through two commands of the station interface. `handOver(to:)` starts the handover, or reports on the one under way. From then on the engine refuses every new turn, saying where the station is going: a prompt, a new session, a scheduled run, and a denial's reason (which would go on as a prompt). It tells every client with the host event `handoverStarting(successor:)`, runs the host's `onHandoverStarted` once (the host stops its upkeep there), and answers with the turns still running (`StationHandoverStatus`). Asking again reports again. The engine remembers which client asked. If that client goes away before the host has let go (the GUI's takeover window was closed, or the GUI crashed), the handover is given up: new turns run again, the host's `onHandoverAbandoned` runs (the daemon starts its upkeep again), and the next list no longer says the station is moving. `releaseStation()` is refused while a turn runs. Once none is left, it answers first, then runs the host's `letGo`. A host with no `letGo` refuses to be asked: that is the GUI while it runs.
- **The side taking over.** `StationHandover` (core) drives a host through a client of it. It asks until no turn is left, then tells the host to let go. A host that goes away before it answers has let go as told. Turns still running after a short wait (3 seconds) move it to `asking`. The person can then wait (`keepWaiting`) or stop the turns (`stopTurns`), which stops each one and keeps what it has done. The handover then carries on once they have gone. A turn that starts after the stop (the GUI's own prompt as it quits), or turns still running a short wait after it, move it back to `asking`, so the person is never left with a handover that is stopping and nothing on screen. It claims nothing: whoever runs it claims the lock with `StationLock.claimOnceReleased`, which retries until the old host's release.
- **Daemon to GUI.** A GUI that finds a daemon in the lock starts under `StationTakeoverLaunch` instead of building its stores. It connects to the daemon's socket, runs the handover, claims the lock and then starts the app as usual. The daemon's `letGo` is its `shutdown`: stop serving, the quit sweep, save, clear the endpoint and release the lock. Its `onHandoverStarted` stops its upkeep. Clients reconnect to the GUI's endpoint by the reconnect path above, which resubscribes the list and host events and reopens their sessions. A daemon that takes the connection but does not answer the handshake (the client gives up on it after its short patience) is not a failure: the takeover window says the service isn't answering, offers to stop it (as for a service of another version) or quit, and waits while the client keeps trying. Once the service answers, the Dialog goes and the handover starts again.
- **A daemon of another build.** An updated GUI cannot ask a daemon of the old build to hand over, since the daemon refuses its handshake. The takeover window says so and offers to stop the service. Stopping it (`StationLock.stopHolder`) sends SIGTERM to the pid in the lock, which the daemon answers as it answers `kill`: its turns stop, it saves, sweeps and releases the lock, and the GUI claims the station once it is free. Choosing Quit leaves the daemon where it was.
- **GUI to daemon.** A GUI that quits with a client attached or a session busy (`GUIStationHost.needsSuccessor`) answers the quit with "later". It runs the same handover on its own engine through an in-process client. Its `letGo` lets the quit go on: the usual save, sweep and release, after which it starts `code-station daemon`, detached, from beside its own binary (`StationDaemon.launch`). The daemon claims the free lock and serves, and clients reconnect to it. With nobody attached and nothing busy, or no `code-station` beside the app, the GUI quits as it always has. `build-app.sh` puts `code-station` in the bundle. After a "later", AppKit waits for the answer in a run loop of its own inside `terminate`, and the handover, the Dialog and the handshakes of terminals starting meanwhile all run on the main queue. So the app never asks to quit from a main-queue block, where that loop could not run the main queue: closing the main window and taking an update ask through the run loop (`AppQuit.request`). While it hands over, the GUI keeps answering handshakes: a terminal that starts then is welcomed, is refused new turns with where the station is going, and follows the station to the daemon by the reconnect path. A handshake refused for handing over would be final for the client, which is worse than a short wait.
- **The running-turns Dialog.** `StationHandoverPrompts` shows `Dialog.runningTurns` in whichever window the handover runs in: the takeover window at launch, or the main window as the app quits. A main window closed to quit comes back to ask, each time the handover asks, the moment it does. The Dialog lists the turns, and offers to wait for them or stop them. Once the person chooses to wait, it keeps only the way to stop.
- **Running turns.** A running turn never moves between processes. Sessions resume on the next host the way they resume after a restart (ADR-0001). A prompt already queued behind a running turn still runs before the handover finishes. Prompts left in the queue by a stop are lost with the old host's process, as on a quit.

## Alternatives considered

- **The GUI as a pure client of a daemon, always.** One host model and no handover. But the GUI's roughly 38 files that read the store and runner directly would have to work through a mirrored store over the socket. That deserves a spec of its own. Handover gives the same experience for now.
- **WebSocket or HTTP on loopback TCP, as the phone uses.** We already have the code. But a TCP port is reachable by every local user and needs a secret to guard it, while a Unix socket gets file permissions and the kernel's peer uid. Framing on a local stream adds nothing.
- **Length-prefixed binary frames.** Faster to split, but JSON lines can be read with `nc -U` while debugging, and messages are small next to what the agents themselves stream.
- **One stream per subscription kind instead of request ids as subscriptions.** It is simpler for the list, but a client can hold several lists and sessions, and reopening a session must end only its own earlier stream. Using the opening request's id names each stream without a second id space.
- **Running one client's requests strictly one at a time.** Every client would see the ordering it sees in process. But one slow sync, find in files or new session held up the stop or permission answer the person sent next. Requests now start in arrival order and run side by side, which keeps the order of commands that answer at once; only stream requests keep strict order among themselves.
- **`launchd` or `SMAppService` to start the daemon.** It would start at login and restart after a crash. The spec leaves login items out. Starting the daemon on demand needs no registration and works from a development build. `SMAppService` can be added later without changing the protocol.
- **Restarting the daemon from a client after a crash.** It would bring the station back unattended. But a crash may recur, two clients would race to start hosts, and handover needs clients that wait rather than claim. A new TUI starts one anyway.

## Consequences

- **Version coupling.** A TUI and a host from different builds refuse each other. Development builds report their build as `development`, so a development TUI attaches only to a development host.
- **Zombie processes.** The TUI that started the daemon is its parent until the TUI exits. If the daemon exits first, it stays a zombie until then. This is harmless and short-lived.
- **Background work.** Schedules, the old-session sweep, the orphaned-worktree monitor, finishing pending deletions and launch housekeeping live in the core (`StationUpkeep`). Every host starts them: the GUI from its app delegate, the daemon from its main. A scheduled run that needs confirmation waits in its task's schedule, shown in the directory, and any front end answers it (`confirmScheduledRun`). The daemon still exits after its idle grace, so a schedule only runs while some host is up, as it only ran while the GUI was open before.
- **Tests.** Every station scenario runs over the socket as well as in process. Socket-only behaviour has scenarios of its own in `StationSocketTests`: the handshake, a host that never answers it, the peer check, file mode, the short path, requests sent with the hello, reconnecting, idle exit, and discovery. `StationHandoverTests` covers the handover: new turns refused, letting go only once turns end, asking and stopping after the short wait, and a client following the station from a daemon to the GUI, and a takeover that waits out a silent daemon. `GUIStationHostTests` covers the GUI quitting to a daemon with a terminal attached, and quitting by closing the window with a turn running: the window comes back with the Dialog, both choices hand over, and a terminal starting meanwhile is answered.
- **Handover is not instant.** A GUI that opens over a busy daemon waits on its turns, or asks, before its window appears. A quit with terminals attached takes as long as the old host's save and sweep, plus the daemon's start.
